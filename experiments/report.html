Each bar shows the proportion of calls that are internal (grey), from a specific named peer microservice (red/orange), or from an anonymous external client (blue). Functions whose red/orange segment alone exceeds the 65% threshold are flagged for relocation. Entry-point functions (e.g. POST /loans) are legitimately 100% external — but their caller is anonymous, not a named peer, so the analyzer correctly keeps them.

Figure 4 — Detection Rate vs. Trace Volume (RQ2)

Detection rate (%) of known-misplaced functions at increasing trace sample sizes. A value of 100% means all misplaced functions were correctly identified at that volume. The earliest N where rate = 100% is the minimum reliable trace volume.

Figure 5 — Observed Calls per Misplaced Function vs. Trace Volume (RQ2)

Number of cross-service calls observed for each known-misplaced function as the trace sample size grows. Even at N=5 traces, at least one call per function is observed — sufficient to establish the 100% external call ratio.

Figure 6 — Precision & Recall vs. Detection Threshold (RQ3)

Precision and Recall at external-call thresholds from 40% to 95% (confidence margin fixed at 5%). Flat curves indicate the classifier is threshold-robust for the evaluated dataset: all misplaced functions exhibit ≥ 99% external call ratios, so any threshold ≤ 99% yields identical decisions. The single persistent FP (GET /books/:id) arises from service-ownership ambiguity — not addressable by threshold tuning.

Figure 7 — F1 Score vs. Detection Threshold (RQ3)

Harmonic mean of Precision and Recall across the threshold range. The constant F1 = 88.9% across all thresholds confirms that the chosen default (65%) is not a special optimum — it is simply a reasonable lower bound that avoids flagging functions with moderate (50–64%) external call ratios until sufficient evidence has accumulated. The vertical dashed line marks the plugin default (65%).
