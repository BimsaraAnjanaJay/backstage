⚠ False Positive Analysis: GET /books/:id is exclusively called by loan-service (98.4% dominant), triggering the relocation flag. However, it exposes a general book-retrieval interface appropriate to book-service. This FP arises from high coupling without misplacement — a pattern not distinguishable from true misplacement using call-ratio analysis alone. Future work: ownership-aware annotations or interface-classification heuristics.

Figure 4 — Cross-service vs. Internal Call Volume per Function

Absolute call counts over 447 traces. POST /members/:id/validate accumulates the highest cross-service call count (294), reflecting that member validation is invoked on every loan creation and return operation.

Figure 5 — Average Span Latency: Internal vs. Cross-service Calls

POST /loans shows the highest cross-service latency (≈20 ms) as it orchestrates calls to both book-service and member-service per loan creation. The misplaced functions show relatively low individual latency (≈4 ms each) but their cumulative cost is significant given their high call frequency.

RQ2 — Trace Volume Sensitivity

Figure 6 — Detection Rate vs. Trace Volume

Both misplaced functions are detected at N = 5 traces. The loan workflow exercises both misplaced endpoints on every transaction, so even minimal traffic is sufficient to establish the 100% external call ratio. Detection remains stable through all 447 traces.

Figure 7 — Cross-service Calls per Misplaced Function vs. Trace Volume

POST /members/:id/validate grows at 2× the rate of POST /calculate-late-fee because member validation is triggered on both loan creation and loan return, while late-fee calculation only triggers on return operations.

RQ3 — Threshold Sensitivity Analysis

Figure 8 — Precision & Recall vs. Detection Threshold

Recall stays constant at 100% across all thresholds — both misplaced functions have 100% external call ratios and are flagged regardless of threshold. Precision is constant at 66.7% because the single FP (GET /books/:id, 100% external) is equally unresolvable at any threshold in this range.

Figure 9 — F1 Score vs. Detection Threshold

F1 = 80.0% across all thresholds 40%–95%. The persistent FP is a structural issue (ownership ambiguity), not a tuning issue. The dashed line marks the plugin default (65%).

Key Findings — Experiment 2

  • RQ1: Precision = 66.7%, Recall = 100%, F1 = 80% across 7 labelled functions.
  • RQ1: Both misplaced functions correctly identified — POST /calculate-late-fee (book-service) and POST /members/:id/validate (member-service) — both recommended for relocation to loan-service.
  • RQ1: One false positive — GET /books/:id (book-service) — flagged due to exclusive usage by loan-service despite being semantically appropriate in book-service. Represents a high-coupling / not-misplaced pattern.
  • RQ1: Entry-point functions POST /loans and POST /loans/:id/return are 100% externally called but correctly kept (caller is anonymous client, not a named peer).
  • RQ2: Both misplaced functions detected at the minimum sample of N = 5 traces. Stable detection across all 447 traces.
  • RQ3: Performance is constant across all thresholds 40%–95%. The FP is not resolvable by threshold tuning — requires service-ownership metadata or semantic analysis.
